## 3. Why This Concept Exists

Real programs are not one file forever. Packages prevent name collisions and organize code. Classpath rules decide what the JVM can load. JShell shortens the feedback loop for trying language ideas. Master these before Spring Boot project wizards hide them.

## 4. Conceptual Explanation

### 4.1 Packages

A **package** is a **namespace** for types (classes, interfaces, enums, …). It solves two problems at once:

1. **Name collisions** — Two teams can both have a `User` class if one is `com.acme.User` and the other is `com.contoso.User`.
2. **Organization** — Folder structure on disk reflects logical modules (`app` for entry, `util` for helpers).

Declaration at the top of a `.java` file:

```java
package app;
```

**Directory rule:** If the first line is `package app;`, the file must live under an `app/` folder: `app/App.java`. The JVM’s binary name for the class is `app.App` (package dots + class name). If package and folder disagree, `javac` fails or you get confusing “wrong package” errors.

**Default package:** A file with no `package` line is in the unnamed default package—fine for one-file demos, discouraged in real projects because other packages cannot import from it cleanly.

Convention in industry: reverse-domain style (`com.example.app`). This handbook’s `classpath-demo` uses short names `app` and `util` to keep paths readable.

### 4.2 Compiling to an output tree

```bash
javac -d out app/App.java util/Greeter.java
```

`-d out` writes class files into `out/app/App.class` and `out/util/Greeter.class`, preserving package structure.

### 4.3 Classpath and the classpath-demo story

The **classpath** is an ordered list of **directories and/or JAR files** where the JVM looks for `.class` files for *your* code. Platform classes (`java.lang.String`, etc.) come from the JDK itself and are not something you put on the classpath manually.

**Narrative (classpath-demo):** The example under [examples/beginner/classpath-demo/](../examples/beginner/classpath-demo/) has two source files in two packages:

| Source file | Package | Depends on |
|-------------|---------|------------|
| `util/Greeter.java` | `util` | nothing in the demo |
| `app/App.java` | `app` | `util.Greeter` via `import util.Greeter;` |

**Step 1 — compile into a tree:** From the demo root:

```bash
javac -d out app/App.java util/Greeter.java
```

`-d out` means “write every `.class` under `out/`, preserving packages.” You get `out/util/Greeter.class` and `out/app/App.class`. Source stays in `app/` and `util/`; generated bytecode is **separate** in `out/`.

**Step 2 — run with an explicit classpath:** The shell’s current directory is usually the demo root, **not** `out/`. The JVM will not magically look inside `out` unless you say so:

```bash
java -cp out app.App Handbook
```

- **`-cp out`** — search the `out` directory when resolving `app.App` and `util.Greeter`.
- **`app.App`** — **binary name** with dots (package + class), not a filesystem path like `out/app/App`.
- **`Handbook`** — first command-line argument; becomes `args[0]` in `App.main`.

**Verified result:** `Hello, Handbook!`

**What `import` does here:** At compile time, `import util.Greeter` lets you write `Greeter.greet(...)` instead of `util.Greeter.greet(...)`. It does **not** copy source and does **not** add folders to the classpath. At run time, the JVM must still find `util/Greeter.class` on the classpath—both classes must live under the same `out` root you passed to `-cp`.

**Why single-file demos hid this:** With no `package` and `.class` beside `.java`, the default classpath entry `.` (current directory) is enough. Packages plus `-d out` break that assumption on purpose so you learn the explicit pattern early.

```mermaid
flowchart LR
  src[app/ and util/ sources]
  outdir[out/ class tree]
  jvm["java -cp out app.App"]
  src -->|"javac -d out"| outdir --> jvm
```

**Wrong directory failure:** `java app.App` without `-cp out` (from the demo root) typically yields `Could not find or load main class` because the launcher searches `.` and does not see `app/App.class` at the root—only under `out/`.

### 4.4 Simple project layout (pre-Maven)

```text
classpath-demo/
  app/App.java
  util/Greeter.java
  out/                 (generated; do not commit)
```

Later, Maven/Gradle use `src/main/java` and `target`/`build` (Module 29). Same package idea; more conventions.

### 4.5 JShell — purpose and limitations

**JShell** is the JDK’s official **REPL** (Read-Eval-Print Loop): you type Java snippets at a prompt, the tool compiles and runs them immediately, and prints results—no `public static void main`, no project file, no `javac` step for each line.

```text
jshell
jshell> 1 + 1
$1 ==> 2
jshell> String name = "Handbook";
name ==> "Handbook"
jshell> /exit
```

**Good uses:**

- Check API return types and method behavior (`"hi".length()`, `List.of(1,2).get(0)`).
- Prototype a loop or regex before moving it into a class.
- Learn language features interactively alongside handbook chapters.

**Limitations (why you still need real projects):**

| Limitation | Practical impact |
|------------|------------------|
| No persistent app structure | No packages, build layout, or multi-file workflow—just snippets. |
| Different “scratch” context | Variables and snippets exist in JShell’s session; copying to `.java` files needs a real class structure. |
| Not how servers/CI run code | Production runs `java -cp ...` or JARs, not an interactive shell. |
| Advanced classpath/modules | You can configure classpath in JShell, but multi-module apps are easier in a project (Module 29). |
| Side effects are real | Opening files or calling network code in JShell still affects your machine—treat it like running any Java code. |

Use JShell as a **lab bench** beside solid `.java` files, `javac -d out`, and `java -cp`. When an experiment grows past a few lines, move it into a class in the demo layout above.

## 6. Syntax and Language Rules

```java
package util;

public class Greeter {
    public static String greet(String name) {
        return "Hello, " + name + "!";
    }
}
```

```java
package app;

import util.Greeter;

public class App {
    public static void main(String[] args) {
        String name = args.length > 0 ? args[0] : "world";
        System.out.println(Greeter.greet(name));
    }
}
```

`import` lets you write `Greeter` instead of `util.Greeter`. It does **not** load code by itself—classpath still must contain `util.Greeter`.

### 7.3 Incorrect classpath (predict)

| Mistake | What goes wrong |
|---------|-------------------|
| `java app.App` from demo root without `-cp out` | Launcher looks in `.`, not `out/` → `Could not find or load main class`. |
| `java out/app/App` | Treats `out/app/App` as a class name, not a path → load error. |
| Compile only `App.java` | `javac` may fail or run fails if `util.Greeter` was never compiled into `out/`. |

**Fix:** Always `-cp out` from the demo root with main class `app.App`, or `cd out` and run `java -cp . app.App` so the classpath root matches where `app/` and `util/` folders of `.class` files live.

## 9. Internal Behavior

The JVM loads classes by binary name (`util.Greeter`) using class loaders that consult the classpath/module path (Module 26). Package directories on disk match binary names for ordinary directory-based classpaths.

## 10. Edge Cases and Limitations

- Default package (no `package` line) is OK for tiny demos; avoid it in real projects
- JAR packaging changes how classpath entries look (`-cp app.jar`)
- Module path (`JPMS`) adds another dimension—Module 29

## 11. Common Mistakes

### Incorrect

`package app;` but file lives in the wrong folder.

### Corrected

Match directory and package.

### Incorrect

`java out/app/App` 

### Corrected

`java -cp out app.App`

### Incorrect

Assuming `import` copies source into your file.

### Corrected

`import` is a compile-time name shortcut; classes load via classpath.

## 12. Best Practices

- One public top-level class per file; file name matches class.
- Generate classes into `out/` / `target/`; don’t commit `.class` files.
- Use JShell for experiments; commit real programs as `.java` files.

## 13. Design Trade-offs

| Layout | Benefit | Cost |
|--------|---------|------|
| Flat default package | Fast demos | Collisions; poor scaling |
| Packages + `-d out` | Clear | More commands |
| Maven/Gradle | Standard | Learning curve (Module 29) |

## 14. Performance Considerations

## 15. Security Considerations

Never put untrusted directories first on the classpath (class shadowing). Production uses build-managed dependencies (Module 29, 43).
